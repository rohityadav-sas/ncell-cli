ncell-cli

A command-line client for Ncell Nepal self-care, written in Rust. It supports OTP login, balance and profile queries, plan search, subscriptions and free SMS.

Features

Simple login

SMS OTP with hidden input and a reusable device identity.

Local credentials

Tokens are stored in your system keyring, with no plaintext fallback.

Human and machine output

Readable tables by default, structured JSON with --json.

Example

ncell search "SMS" --tag 50 --sort price
ID    Plan                      Price     Validity
984   1 Day: 100 All Net SMS    Rs. 15    1 DAY
985   7 Day: 300 All Net SMS    Rs. 45    7 DAY
986   28 Day: 300 All Net SMS   Rs. 98    28 DAY

Illustrative output. Offers, prices and eligibility come from Ncell's server.

Installation

Install stable Rust and Git. Clone the repository and install the executable on your PATH:

git clone https://github.com/rohityadav-sas/ncell-cli.git
cd ncell-cli
cargo install --path . --locked
ncell --help

Prefer a prebuilt executable? Download the Windows x86_64 release, extract the ZIP, and run .\ncell.exe --help in a terminal from the extracted directory. Add that directory to your PATH if you want to run it anywhere. macOS and Linux currently build from source.

No Android phone or root access is needed for normal CLI use. See the changelog for release history.

Authentication

Sign in with an SMS code:

ncell login 98XXXXXXXX

Use a ten-digit Nepal mobile number, optionally prefixed with +977. The command requests an OTP and prompts for it without echoing the input. The number must be eligible for Ncell self-care login.

  1. A local device ID is generated or reused, then saved before the OTP request.
  2. Ncell sends the SMS code. Enter it at Enter OTP:.
  3. The CLI validates it with the same device ID and saves the returned tokens in your native keyring.

Resume instead of resending

ncell login 98XXXXXXXX --verify

Use this after an interruption or mistyped OTP. It resumes the pending login for that number without generating another SMS. For an expired code, run normal login again. There is no automatic OTP resend.

Note

Only one account and one pending login are stored. A failed login preserves the previously authenticated account. Run one login process at a time.

Inspect or remove the saved session

ncell status
ncell logout

status checks local storage, not server token validity. logout deletes the local session and device ID; it does not revoke tokens on Ncell's server.

Balance and profile

ncell balance
ncell balance --json
ncell profile
ncell profile --json

Balance output summarizes credit, data, voice and SMS. JSON returns the complete balance response object, including details and expiry information supplied by the server.

Profile output shows the account number, name, SIM type, status, plan and payment mode when provided.

Profile statusCLI label
B01Active
B03All Services Blocked
B04Outgoing Blocked
B02 / otherShown unchanged; meaning is not confirmed

These labels use the profile's status field. They are different from the local login check performed by ncell status.

Warning

Profile JSON can contain private account details, including PIN/PUK information. Review it before sharing logs or screenshots.

Plans and tags

ncell plans
ncell plans --list-tags
ncell plans --tag 50
ncell plans --tag 61
ncell plans --tag 66 --json

The default tag is 66. The CLI lists the current catalog for your account, showing plan ID, name, price and validity. Prices omit a trailing .00; fractional amounts remain intact, and free packs display Free.

TagCatalog
50SMS
61Voice
66Data & Voice (default)

Use --list-tags for the full, current list. Different categories may use the same label, such as “All Packs”, while their IDs identify different catalogs. An empty tag is possible for an account; a listed tag does not guarantee available offers.

Non-default tags are resolved from the server's category list. For a tag with multiple categories, data takes priority, followed by voice and SMS. Unknown or unsupported categories return an error. Tag listing cannot be combined with an explicit tag, search or sorting options.

Search and sorting

ncell search "SMS" --tag 50
ncell search "Super" --sort price
ncell plans --search "Combo" --sort validity:desc,price:asc

Search sends the keyword to Ncell's catalog endpoint. It is server-side and scoped to the selected tag, not a local text filter or an all-catalog search. Omitting --tag searches tag 66. An empty keyword is rejected; no matches produce an empty catalog.

Sort by more than one field

ncell search "SMS" --tag 50 --sort validity:desc,price:asc
ncell plans --sort validity:desc --sort price:asc
ncell plans --sort validity,price

Supported fields are price and validity. Directions are asc and desc; omitted directions mean ascending. The default is ascending price.

Keys are applied left to right: validity:desc,price:asc means longest validity first, then lowest price among plans with equal validity. Repeated --sort flags and comma-separated keys are equivalent. Sorting runs locally after the server response and applies to JSON too. Durations in minutes, hours, days and weeks are compared on a common scale.

Subscribe to a plan

ncell plans --tag 50
ncell subscribe --tag 50 --id 984

Use the plan ID from the catalog and the same tag that listed it. --id is required; --tag defaults to 66. A tag ID is not a plan ID.

Warning

This command submits a subscription request immediately. Paid packs charge your Ncell balance. Check the current catalog and price first.

The CLI fetches current plan metadata, including subscription code, name and price, then submits the subscription using the saved login device ID. Successful plain output is Subscribed to <plan name>. Use --json for the complete subscription response.

HTTP success with billing code BIL1000 is recognized as success, even when responseCode is 00. Network and business errors are not automatically retried; explicit token expiry can trigger the one-time authenticated refresh workflow.

If a request times out, check balances or the app before manually submitting it again. The operation may have reached the server.

Free SMS

ncell send-free-sms 98XXXXXXXX "Hello"
ncell send-free-sms 98XXXXXXXX "Hello" --json

The recipient must be a ten-digit Nepal mobile number, optionally prefixed with +977. Message text must not be blank. Eligibility and remaining free SMS allowance are controlled by Ncell.

Plain success output is SMS sent to <number>. JSON returns the server response. The CLI checks the inner SMS status, because an outer successful response code does not always mean the message was sent.

Business and network failures do not trigger a resend. An explicit expired-access-token rejection can trigger one refresh and retry.

JSON output and scripting

ncell --json balance
ncell plans --tag 50 --sort price --json
ncell profile --json

--json is global and works before or after any command. It changes output formatting, not whether the command buys a pack, sends an SMS or changes the session.

ResultOutputExit status
SuccessJSON on stdout0
Ncell rejectionFull server JSON on stdoutNonzero
Local or network errorJSON error on stderrNonzero
Argument errors / helpClap's standard formattingDepends on invocation

Balance and profile return their response object. Catalog and subscription commands preserve their server response. Local commands, login and refresh return operation status without exposing tokens. OTP prompts remain interactive and outside JSON stdout.

PowerShell example

$raw = ncell plans --tag 50 --json
if ($LASTEXITCODE -eq 0) {
    $catalog = $raw | ConvertFrom-Json
    $catalog.availablePackages
}

Check the exit status before treating JSON as a successful result. Server rejection JSON has a different structure from the successful catalog.

Sessions and token refresh

Tokens and device identity are stored under service ncell-cli, entry session, in your platform's native credential store. OTPs are not persisted. There is no plaintext storage fallback.

Automatic refresh

  1. An authenticated request is rejected with HTTP 401 and LGN2001.
  2. The saved refresh token and matching device ID are used to refresh.
  3. New tokens are saved before the original operation is retried once.

A failed refresh preserves the previous session and stops. A second expiry response is returned without looping. Other authentication, business and network errors are not replayed. Automatic refresh applies to balance, profile, plans, search, subscriptions and free SMS.

Manual refresh

ncell refresh
ncell refresh --json

The CLI saves the new access token and any new refresh token returned by the server. If no replacement refresh token is returned, the existing one is retained. A missing saved refresh token requires login again.

Note

If the mobile app and CLI share a login, token rotation can invalidate the app's old tokens. Synchronize the new tokens before using that shared session again. The CLI does not synchronize automatically.

Import a session

import-session reads JSON from standard input. The device ID must match the login that produced the tokens.

{
  "device_id": "<matching login device ID>",
  "account": {
    "msisdn": "<10-digit number>",
    "access_token": "<access token>",
    "refresh_token": "<refresh token>",
    "authenticated_at": "<ISO UTC timestamp>"
  }
}
# PowerShell
Get-Content -Raw session.json | ncell import-session

# Unix shell
ncell import-session < session.json

Keep any session files private. Normal login writes directly to the system keyring.

Local Android bridge (optional)

.\sync_token.ps1 mobile-to-cli
.\sync_token.ps1 cli-to-mobile

The Windows bridge script and its sibling ../bypass/scripts/pull_tokens.ps1 / push_tokens.ps1 helpers are local tools and are not included in the repository. They require the separately configured rooted Android device, adb and Python setup, plus a release CLI build.

Mobile import preserves the number and device ID. Pushing tokens restarts the app through the helper. Neither direction requests an OTP or refreshes tokens.

Troubleshooting

ncell doctor

Doctor makes a HEAD request without submitting a number, sending an OTP or reading credentials. Any HTTP response proves an HTTPS connection was established; a 405 is expected from an endpoint that normally accepts POST. This is a connectivity check, not proof that account APIs are healthy.

The client uses a 45-second connect timeout and a 90-second overall timeout. Network failures are returned without automatic retries.

Code / errorMeaning / next step
LGN2000Mobile number is missing.
LGN2001Access token expired; authenticated commands attempt one refresh.
LGN2002Authentication token was not supplied.
LGN2003Authentication error; exact meaning unconfirmed. No automatic refresh.
LGN2004Invalid refresh token or a mismatched device ID. Re-establish a matching session.
LGN2005Number change is not allowed.
LGN2007Invalid mobile number.
LGN2009Request validation failed; a required field may be missing.
LGN3000Unable to process the request; try again later.
BIL1000Subscription success when returned with HTTP success.
BIL2006Duplicate subscription request; wait before retrying.
PSU2001Subscriber cannot subscribe/unsubscribe in the current state, as observed in a captured response.
Storage unavailableUnlock your system credential store; check Secret Service and session D-Bus on Linux.
No pending OTPRun normal login for the number first, then resume with that same number.
Plan not foundUse a plan ID and the tag that listed it. Tags and plans have separate IDs.

Plain errors preserve HTTP status and the server code with safe static labels. Use --json for the original server rejection body. Unknown codes are not assigned guessed meanings.

API and request design

The shared blocking HTTP client calls https://sca.ncell.com.np/adl/et/telco/selfcare/ncell/api. Requests use JSON content type and bearer authentication where required, plus library-managed transport headers. Redirect following is disabled.

OperationPOST path
Generate OTP/v1.0/user/otp/generate
Validate OTP/v1.0/user/otp/validate
Refresh/v1.0/user/refresh/token
Balance/v1.0/accountmgt/balance/query
Profile/v1.0/subscriber/profile/query
Tags/v1.0/product-catalog/tags
Catalogs / search/v1.0/product/{data|voice|sms}-plans
Subscribe/v1.0/billingmgt/product/subscribe
Free SMS/v1.0/smsmgt/free/sms/send

Retained request fields

The common JSON requestHeader has ten fields: requestId, timestamp, channel, deviceType, clientip, action, msisdn, location, primaryMsisdn and languageCode. Individual omission checks established their necessity on OTP, balance, profile, tags, catalogs and refresh for the tested flow.

  • OTP generation retains number, device ID and login action. Validation retains number, device ID, nested action and OTP.
  • Balance retains the number in its query object.
  • Profile accepts an empty query object, but requires the object and app-version header.
  • Tags retain app version; omitting it silently hid a tag in live checks.
  • Catalogs retain number, language, tag, sortby.name and the common header. A keyword is added only for search.
  • Refresh retains the refresh-token object and matching device ID in the header.
  • SMS uses destination, content and isConfirm: 0. Omitting the confirmation field failed despite an outer success code.
  • Subscription retains captured metadata pending further omission tests.

Note

Individual common-header omissions for SMS and further subscription-field omissions remain unverified. “Minimum” describes observed checks, not every possible server behavior. API requirements can change.

Development

├── api/          HTTP transport and request builders
├── session/      Session models and native keyring
├── auth.rs       Login and bounded token refresh

├── error.rs      Safe error labels

Libraries handle the standard work: clap, reqwest, serde, keyring, rpassword, chrono, uuid and thiserror. There is no custom HTTP stack or JWT parser.

cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked

CI checks Windows, macOS and Linux. Source unit tests are included. The local integration-test directory and Android token bridge are ignored and excluded from this repository. Live account operations are separate from automated checks.
